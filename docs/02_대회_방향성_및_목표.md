## 공식 문제 정의

### 주제

**투구 단위의 제구 성공 확률 예측 AI 모델 개발**

### 과제

투구 직전까지 확인 가능한 경기 상황, 선수 정보, 주자 상황, 과거 이력을
바탕으로 테스트 데이터의 각 투구에 대한 `control_success` 확률값을 예측합니다.

- 학습 데이터의 `control_success`: 제구 성공은 `1`, 제구 실패는 `0`
- 제출 데이터의 `control_success`: 제구 성공 가능성을 나타내는 `0~1` 확률
- 모델 입력: 해당 투구 이전 시점에 활용 가능한 정보로 제한

### 공식 제구 성공·실패 기준

온라인 해커톤 Phase 2의 제구 성공 여부는 각 투구의 공 위치를 기준으로
정의됩니다. 다음 세 경우는 제구 실패(`control_success = 0`)입니다.

1. 스트라이크존 가운데 부근으로 들어간 공
2. 스트라이크존에서 크게 벗어난 공
3. 포수의 요구 방향과 반대로 들어간 공

위 세 경우에 해당하지 않는 유효한 투구는 제구 성공(`control_success = 1`)입니다.

이 정의에서 중요한 점은 단순히 스트라이크인지 여부를 예측하는 문제가 아니라는
것입니다. 스트라이크존 가운데에 몰린 공은 실패일 수 있고, 존 밖의 공이라도 크게
벗어나지 않고 요구 방향에 부합하는 유효한 투구라면 성공일 수 있습니다.

### 대회 단계

Phase 2는 교육생의 문제 해결 능력을 검증하여 Phase 3 진출자 약 100명을 선발하는
온라인 해커톤입니다. Phase 3는 1박 2일 오프라인 해커톤으로 진행되며 세부 과제는
추후 안내됩니다. Phase 3 역시 야구 데이터를 기반으로 한 AI 문제입니다.

## 🎯 이 대회가 원하는 것 (핵심 목표)

### Target Variable: `control_success`

**각 투구(pitch)가 "제구에 성공했는가"를 예측하는 이진 분류 문제**

| 구분 | 값 | 의미 |
|------|-----|------|
| 학습 (train.csv) | `0` or `1` | `1` = 제구 성공, `0` = 제구 실패 |
| 예측 (제출) | `0.0 ~ 1.0` | 제구 성공 **확률** (예: `0.73`) |

---

## ⚾ 공식 정의와 입력 피처의 연결

`train.csv`의 다음 과거 이력 피처는 공식 실패 기준과 직접 연결되는 중요한
입력입니다. 이 값들은 현재 투구의 결과가 아니라 해당 투구 직전까지 집계된
공식 `asof_*` 피처이므로 사용할 수 있습니다.

| 공식 실패 기준 | 관련 과거 이력 피처 |
| --- | --- |
| 스트라이크존 가운데 부근 | `asof_pitcher_middle_rate`, 최근 1·3·5경기 middle rate |
| 스트라이크존에서 크게 벗어남 | `asof_pitcher_ball_rate`, `asof_pitcher_strike_rate` |
| 포수 요구 방향과 반대 | `asof_pitcher_reverse_rate` |

현재 투구의 실제 위치, 실제 판정, 실제 구종, Trackman 측정값 또는 포수 요구 대비
실제 방향은 사후 정보이므로 입력으로 사용할 수 없습니다.

## 📦 데이터 구성 & 역할

```
데이터셋 구조
├── train.csv          → 학습 데이터 (정답 control_success 포함, 49개 컬럼)
├── test.csv           → 예측 대상 (정답 없음, 상황 정보만 존재)
├── trackman_history.csv → 과거 투구 물리 데이터 (트랙맨 센서 기록)
└── sample_submission.csv → 제출 형식 예시
```

### 각 파일의 역할

| 파일 | 역할 |
|------|------|
| `train.csv` | 경기 상황 + 투수/타자 과거 누적 통계 + 정답(`control_success`) |
| `test.csv` | 정답 없이 경기 상황만 주어짐 → 여기서 `control_success` 예측 |
| `trackman_history.csv` | 투수별 물리적 투구 특성(스핀, 속도, 변화량) → **파생변수 소스** |

## 🧠 모델이 풀어야 하는 핵심 질문

> **"현재 경기 상황과 투수의 폼을 고려했을 때, 이 공이 제구대로 잘 들어갈까?"**

이를 풀기 위해 3가지 관점의 데이터가 제공됩니다:

---

### 관점 1️⃣ 심리적/환경적 압박감 (경기 상황)

| 컬럼 | 의미 |
|------|------|
| `inning` | 이닝 (후반일수록 피로 + 압박 증가) |
| `score_diff_pitcher_team` | 점수 차 (지고 있을수록 압박감 ↑) |
| `num_runners_on` | 루상 주자 수 (만루일수록 극도의 긴장) |
| `li` | 레버리지 인덱스 — 현재 상황의 중요도 수치화 |
| `runner_on_1b/2b/3b` | 각 베이스 주자 여부 |

**핵심 인사이트:** 압박 상황에서 제구가 무너지는 투수 vs 오히려 강해지는 투수를 분류해야 함

---

### 관점 2️⃣ 투수의 현재 컨디션 / 폼 (누적 & 최근 기록)

| 컬럼 | 의미 |
|------|------|
| `asof_pitcher_success_rate` | 현재 시점까지 누적 제구 성공률 |
| `asof_pitcher_prev1_game_success_rate` | 가장 최근 1경기 제구 성공률 |
| `asof_pitcher_prev3_game_success_rate` | 최근 3경기 제구 성공률 |
| `asof_pitcher_prev5_game_success_rate` | 최근 5경기 제구 성공률 |
| `asof_pitcher_strike_rate` | 현재까지 스트라이크 비율 |
| `asof_pitcher_ball_rate` | 현재까지 볼 비율 |

**핵심 인사이트:** 투수 이름보다 "최근 폼"이 제구 예측에 훨씬 강한 힌트

---

### 관점 3️⃣ 타자 상성 & 구종 패턴

| 컬럼 | 의미 |
|------|------|
| `pitcher_hand` / `batter_hand` | 좌우 투타 매치업 (상성 관계) |
| `asof_pitcher_fastball_rate` | 직구 구사 비율 |
| `asof_pitcher_breaking_rate` | 변화구 구사 비율 |
| `asof_pitcher_offspeed_rate` | 오프스피드 구사 비율 |
| `asof_batter_success_rate` | 타자의 현재까지 제구 성공 유도율 |

**핵심 인사이트:** 특정 타자(강타자)를 상대할 때 도망가는 피칭 → 제구 불안정

## 🔑 trackman_history.csv 활용 전략

`train.csv`에는 없는 **세밀한 물리 투구 특성**이 담겨 있음  
→ 투수별 파생 변수를 만들어 `train.csv`와 **join**해서 사용

| 만들 수 있는 파생 변수 예시 | 설명 |
|--------------------------|------|
| 투수별 평균 `rel_speed` | 해당 투수의 평소 구속 기준 |
| 투수별 `spin_rate` 분포 | 구위 안정성 지표 |
| 투수별 `horz_break` 일관성 | 제구 일관성 (분산이 낮을수록 좋은 제구) |
| 구종별 릴리스 포인트 일관성 | `rel_height`, `rel_side` 분산 |
| 피로도 지표 | 해당 경기 투구 수 대비 속도 저하율 |

## 📊 평가 지표: Brier Skill Score

제출 형식 (`sample_submission.csv`):
```
row_id,control_success
TEST_000001,0.5
TEST_000017,0.72
...
```

- **예측값**: 0~1 사이의 확률값
- **Brier Score**: `mean((p_i - y_i)^2)` — 낮을수록 좋음
- **기준 Brier Score**: 평가 데이터 평균 제구율을 `r`이라 할 때 `r × (1-r)`
- **최종 Score**: `max(0, 100000 × (1 - Brier Score / 기준 Brier Score))` — 높을수록 좋음
- 분류 정확도뿐 아니라 예측 확률의 보정(calibration)이 중요함

## 🗺️ 공략 로드맵

```
Step 1. EDA (탐색적 데이터 분석)
    └── train.csv 분포 확인, control_success 비율, 결측값 처리

Step 2. Feature Engineering (파생 변수 생성)
    ├── trackman_history.csv → 투수별 물리 지표 통계 집계
    └── 경기 상황별 제구 패턴 파생 변수

Step 3. 모델링
    ├── Baseline: LightGBM / XGBoost
    ├── 앙상블: Stacking / Blending
    └── 최신 시도: TabPFN, CatBoost

Step 4. Validation
    └── 시계열 특성 고려 → 미래 경기를 validation으로 사용

Step 5. 제출
    └── submissions/by_submitter/의 담당자 폴더에 submit_v<번호>.zip 배치
```

## ⚠️ 주의사항 (Data Leakage 방지)

> `asof_` 로 시작하는 컬럼들은 **해당 투구 직전까지의 누적 통계**임  
> (즉, 미래 데이터가 섞이지 않은 안전한 피처)  
> 별도로 trackman_history에서 파생 변수를 만들 때도  
> **test 시점 이후 데이터를 포함시키면 안 됨**
